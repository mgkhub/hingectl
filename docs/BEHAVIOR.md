# 実機での挙動と注意点

実機(iPhone Duo)で確かめた内容です。値(待ち時間など)の根拠と、未確認の事項を載せます。使い方は、[README](../README.md) を参照してください。

- ヒンジ角の設定は、Device Hub のヒンジスライダーと同じ vendor-defined HID イベント(usagePage `0xFF61`, usage `0x5B`)で送ります。設定した角度は、コマンドが終了した後も維持されます。
- `orient` / `rotate` は、送信後に向きを繰り返し読み戻して、一致するのを確認します(読み戻しに反映が現れるまで約 0.9 秒)。送信直後にプロセスを終了すると、デバイスに反映されませんでした(待つだけでも、短いと反映されませんでした)。そのため `-t 0` でも、最大 2 秒は読み戻しを続けてから終了します(一致しなくてもエラーにはしません)。
- 現在角が `sweep` の `from` と違う場合は、掃引の前に `from` へ移動して到達を待ち、UI を載せるディスプレイが切り替わって新しい側が点灯してから 0.5 秒待って、掃引を始めます。待たないと、`from` へ一気に飛んだ直後に掃引が始まり、`from` 側のディスプレイのアニメーションが途中で切られます。実機の Duo では、閉じるとき、UI は約 0.7 秒で背面へ切り替わります(内側のバックライトはその後も約 3.5 秒点いたままですが、それを待つと長すぎたため待ちません)。約 1 秒待っても切り替わらない移動では、そこで待ちを打ち切ります(上限 6 秒)。0.5 秒は、0 / 0.5 / 1 秒を実機で比べて決めました。現在角が `from` と一致する場合と、`-t 0` の場合は、待たずに始めます。
- `sweep` は、開始時刻を基準にした各ステップの目標時刻に合わせて 60Hz で送り、最後に 1 回だけ流し切ります。イベントごとに `sendBarrier()` を呼ぶと、1 回に約 17 ms(往復待ち)かかって実効 26Hz 前後になり、指定の 2.2 倍の時間がかかったため、この方式にしました(実機で計測)。修正後は、デバイスが報告する角度が 200ms ごとに一定(180°→90° を 2 秒なら -9.0°)で動きます。
- ヒンジ角も、送信直後に終了すると反映されませんでした(待ちが 0ms で 0/3 回、50ms 以上で 3/3 回)。`-t 0` や `sweep` の終了前に、300ms 待ってから終了します。確認つきの `set` も、現在値がすでに目標の ±0.5° 以内で、購読の最初の値で確認できたとき(角度が動いたわけではないとき)だけ、送信から 300ms になるまで待ちます(動いて確認できたときは、待ちません)。
- `devicectl device orientation set` は、実機の iPhone Duo では画面が回転しませんでしたが、`hingectl orient` では回転します。
- 未確認: `hingectl set` で設定した角度が、実機を手で動かしたときや再起動したときにどうなるか(設定した値が残り続けるのか、物理ヒンジの値に戻るのか)。
